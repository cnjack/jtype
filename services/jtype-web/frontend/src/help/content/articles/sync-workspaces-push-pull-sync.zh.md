同步让已绑定的仓库与其云端工作区保持一致，却绝不会把文件从你手中夺走。磁盘上的本地 Markdown 始终是唯一可信来源——同步只是把改动送上去、把改动取下来。哪怕明天云端和网络都消失了，你的每一条笔记依然完好地躺在一个普通文件夹里。

## 双向：推送与拉取

一旦仓库[绑定到工作区](/help/c/sync-workspaces/cloud-workspaces)，一条命令就能让改动在两个方向上流动：

```bash
jtype sync
```

- **推送（Push）**把你在本地新建或编辑的笔记送到工作区。
- **拉取（Pull）**把云端发生变化的笔记（来自你的其他设备、同事、网页编辑器或 AI 助手）取下来，写入你的仓库。

在桌面应用中，已绑定的仓库会在后台自动同步，所以这一切大多无需操心。命令行则让你按需完成同样的往返，在无界面的服务器上或脚本里尤其顺手。

## 版本，以及拉取为何安全

每条笔记在变化时都带有一个版本号。当你执行 `jtype sync`，JType 会比较版本，**仅当传入内容确实与磁盘上的不同**时才写入文件。这种“先比对再写入”意味着重复同步就是一次空操作——没有文件抖动，没有意外的时间戳，也不会与你正打开的编辑器较劲。拉取绝不会盲目覆盖一个已经一致的文件。

## 当同一条笔记在两处都被改动

**冲突**其实很简单：自上次同步以来，同一条笔记在两处都被编辑过——比如既在你的笔记本上，又在网页上。JType 依据版本来检测，而非靠猜测，因此不会有任何内容被悄悄丢失。

- 在**桌面应用**中，冲突会出现在冲突界面里。能安全合并时，JType 会做三方合并；无法合并时，它会同时展示两边，让你选择保留哪一份。这是你的人工安全网。
- 在**命令行**中，`jtype sync` 会报告发生冲突的路径，而不是覆盖它们，于是你可以打开笔记自行调和。

由于文件的每个版本都是磁盘上的纯 Markdown，最坏的情况也总能恢复：你可以读两边、复制想要的行、再保存。

## 一个简单的流程

```bash
# 在设备 A 上
jtype note update projects/roadmap.md --file ./roadmap.md
jtype sync          # 把你的修改推送上去

# 在设备 B 上
jtype sync          # 把它拉取到本地仓库
jtype note get projects/roadmap.md
```

## 好习惯

- **工作前后各同步一次**，让你从最新版本开始、以最新版本结束。
- **尽量一次只在一台设备上编辑**——这是彻底避免冲突最稳妥的办法。
- **信任你的磁盘。** 如果同步后有任何不对劲，你的仓库文件夹就在那里，可用任意编辑器查看。
