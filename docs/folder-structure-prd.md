# JType 文件夹结构 PRD

日期：2026-05-04

## 1. 背景

JType 当前的文件存储已经支持嵌套目录结构：

- **本地文件系统**：`collect_markdown_files()` 递归扫描目录，`FileTreeNode` 支持 `kind: Folder` 和 `children: FileTreeNode[]`。
- **云端数据库**：文档有 `relative_path` 字段（如 `notes/meeting.md`），但**没有单独的文件夹实体**。文件夹隐式来自文档路径。
- **前端**：`FileTreeNode` 已支持嵌套结构，侧边栏显示平铺文件树。
- **同步**：文档通过 `relative_path` 同步，包含 `/` 的嵌套路径，Rust 后端自动创建父目录。

### 问题现状

但当前**没有明确的文件夹操作能力**：

- 无法创建、重命名、移动文件夹
- 侧边栏不支持展开/折叠树节点
- 删除文件夹没有明确的 UI 和逻辑
- 跨文件夹移动文档依赖复杂的路径编辑
- Web dashboard 也没有文件夹树视图
- 文件夹操作的同步行为未定义

### 为什么重要

文件夹结构是知识管理的基础：

- 让用户能组织大量文档（100+ 笔记时，平铺列表无法使用）
- 反映现实的信息层级（项目 > 主题 > 文档）
- 类似 Obsidian 和 Notion 的用户心智（知识库就应该有树）
- 发布站点时，文件夹可以对应 URL 路径，方便 SEO 和导航

## 2. 竞品分析

### 2.1 Obsidian

- **文件夹是一等公民**：在 File explorer 中显著展示，可新建、重命名、拖拽移动、删除
- **快速打开**：支持按文件夹过滤（如 "folder:projects"）
- **灵活嵌套**：无深度限制，可无限层级嵌套
- **同步友好**：移动或删除文件夹时自动更新所有内部文档的链接和发布路由

### 2.2 Notion

- **分层导航**：左侧 sidebar 支持无限层级页面树，每个页面都可嵌套子页面
- **拖拽重组**：用户通过拖拽改变页面树结构，发布路由也跟着变
- **工作空间隔离**：Workspace > Teamspace > Folder > Database/Page 形成明确的组织层级
- **收藏和快速访问**：Favorites 和 Recent 帮助用户快速定位常用文件夹

### 2.3 Bear

- **标签系统**：不用文件夹，而是用层级标签代替（但支持创建多个标签）
- **快速访问**：最近使用的标签和笔记显示在左侧固定位置
- **简化层级**：避免文件夹过深，而通过标签的灵活组织

### 2.4 JType 的差异化

JType 应该综合 Obsidian 的**本地文件夹可信**和 Notion 的**分层导航便利性**：

- 保留 `relative_path` 作为事实来源，文件夹隐式来自路径
- 提供显式的文件夹 UI 操作（创建、重命名、移动、删除）
- 支持文件和文件夹的拖拽重组
- 发布时文件夹对应 URL 路径

## 4. 核心概念

### 4.1 逻辑文件夹 vs 物理文件夹

- **逻辑文件夹**：由 `relative_path` 的路径部分隐式定义，如 `notes/projects/ai/index.md` 隐含 `notes/`、`notes/projects/`、`notes/projects/ai/` 三个文件夹
- **物理文件夹**：本地文件系统中真实存在的目录
- **设计决策**：数据库中**不存储单独的 folder entity**，始终通过文档的 `relative_path` 来推导文件夹树

### 4.2 文件夹路径

- 文件夹路径规范：使用 `/` 分隔符，路径不包含文件名
  - 有效：`notes/`、`projects/ai/research/`
  - 无效：`notes/meeting.md`（这是文档路径）

- 根文件夹：vault 根目录本身，路径为空字符串或 `/`

### 4.3 文件夹内容归属

一个文件夹的内容包括：

1. 直接子文件：`relative_path` 为 `folder/filename.md` 的文档
2. 直接子文件夹：`relative_path` 为 `folder/subfolder/*` 的文档隐含的直接子目录

**删除文件夹**时的处理：

- **级联删除**：删除文件夹及其所有子文件和子文件夹的所有文档
- **软删除到回收站**：所有被删除的文档移入回收站，可恢复

## 5. 用户故事

### US-1: 组织文档到文件夹

作为知识工作者，我想把相关的笔记组织到不同的文件夹中，这样当笔记数量增加时不会显得混乱。

**场景**：
- 打开 JType，当前所有笔记都在根目录
- 右键侧边栏空白处，选择 "新建文件夹"
- 输入 "projects"，新建成功
- 右键侧边栏的某个笔记，选择 "移动到"，选择 "projects" 文件夹
- 笔记移动到 `projects/` 下，相对路径从 `note.md` 变为 `projects/note.md`

**验收标准**：
- 新建文件夹成功后立即在树中显示
- 拖拽文件到文件夹时路径正确更新
- 本地和云端路径保持一致
- 嵌套文件夹可正常创建（如 `projects/ai/research/`）

### US-2: 快速导航深层文件夹

作为组织能力强的用户，我有 5-8 层深的文件夹嵌套，需要快速打开其中的文档而不是逐级展开。

**场景**：
- 按 `Ctrl+O` 打开快速打开
- 输入文档名或路径片段，如 "research/paper"
- 结果显示文件夹路径，帮助区分同名文档
- 按 Enter 打开，侧边栏自动展开到该文档所在文件夹

**验收标准**：
- 快速打开支持按路径过滤
- 搜索结果显示完整的相对路径
- 打开文档后侧边栏自动展开父文件夹并滚动到该文件

### US-3: 重组织文件夹结构

作为曾经用平铺文件夹的用户，我想重新组织旧的文件夹结构而不丢失任何东西。

**场景**：
- 我有 `meeting_20240101.md`、`meeting_20240105.md` 等散落的笔记
- 右键新建文件夹 `meetings/`
- 逐个拖拽这些文件到 `meetings/` 文件夹
- 所有文件重新路由到 `meetings/meeting_20240101.md` 等

**验收标准**：
- 批量移动操作不会丢失文档
- 移动过程中同步状态清晰
- 移动后在云端也能看到新的路径

### US-4: 发布嵌套文件夹内的文档

作为内容创作者，我的个人网站有 "博客" 和 "研究" 两个栏目，对应本地的两个文件夹。发布后，网站 URL 结构也应该反映这个层级。

**场景**：
- 本地有 `blog/posts/my-article.md` 和 `research/papers/ai-trends.md`
- 发布后 URL 应为 `/u/username/blog/posts/my-article` 和 `/u/username/research/papers/ai-trends`

**验收标准**：
- 发布时保留文件夹路径结构
- Web dashboard 显示完整的文件夹树
- 文件的发布 URL 包含文件夹路径

### US-5: 删除未使用的文件夹

作为整理倾向强的用户，我想清理不再使用的空文件夹或整个项目文件夹。

**场景**：
- 右键 `archive/old-project/` 文件夹
- 选择 "删除文件夹"
- 弹出确认对话框：该文件夹有 5 个文档，是否删除？
- 用户选择 "是，移入回收站"
- 所有文档移入回收站，文件夹消失
- 用户可在回收站恢复这些文档

**验收标准**：
- 删除前明确提示文件夹内容
- 删除后所有文档进入回收站
- 用户可逐个或批量恢复
- 恢复后文件夹也自动重建

## 6. 功能需求

### 6.1 文件夹 CRUD 操作

#### 6.1.1 新建文件夹 (CREATE)

**触发方式**：
1. 右键侧边栏空白处或文件夹，选择 "新建文件夹"
2. 命令面板 "Create Folder"

**逻辑**：
1. 显示输入对话框，默认名称如 "New Folder" 或由用户指定
2. 验证文件夹名称（不包含 `/`、`\`、`:`、`*`、`?` 等非法字符）
3. 在本地创建空目录
4. 更新前端文件树
5. 标记 workspace 为 dirty，触发自动同步
6. 云端无需创建任何实体，下次文档 push 时隐含此文件夹

**验收标准**：
- 新建文件夹名称验证，非法字符被拒绝
- 同一文件夹内不允许重复名称
- 新建后立即在树中可见并可操作

#### 6.1.2 重命名文件夹 (UPDATE)

**触发方式**：
1. 右键文件夹，选择 "重命名"
2. 或在树中双击文件夹名称进入编辑

**逻辑**：
1. 显示编辑框，填充当前名称
2. 用户输入新名称，验证（同创建规则）
3. 本地重命名目录
4. 更新所有子文档的 `relative_path`
5. 更新前端树节点和任何打开的文档的面包屑
6. 标记 workspace 为 dirty，触发 sync
7. 云端比对：发现所有文档路径变化，更新 `relative_path`

**路径更新示例**：
```
本地重命名：meetings/ → meet-logs/

影响的文档：
  meetings/2024-01.md → meet-logs/2024-01.md
  meetings/2024-02.md → meet-logs/2024-02.md
  meetings/archived/old.md → meet-logs/archived/old.md
```

**验收标准**：
- 重命名后所有子文档路径自动更新
- 若有文档因此产生冲突（新路径已占用），显示冲突对话框
- 打开中的文档不会关闭，只更新路径标题

#### 6.1.3 移动文件夹 (UPDATE)

**触发方式**：
1. 拖拽文件夹到另一个文件夹
2. 右键文件夹，选择 "移动到"，选择目标文件夹

**逻辑**：
1. 验证目标位置不是源文件夹的子目录（防止循环）
2. 本地移动目录
3. 更新所有子文档路径
4. 前端树立即反映新位置
5. 标记 workspace 为 dirty，触发 sync

**验收标准**：
- 不允许把文件夹移动到自己的子目录中
- 所有子文档路径正确更新
- 如果目标位置已有同名文件夹，提示覆盖或改名

#### 6.1.4 删除文件夹 (DELETE)

**触发方式**：
1. 右键文件夹，选择 "删除"
2. 或选中文件夹后按 Delete 键

**逻辑**：
1. 检查文件夹是否为空
   - 空文件夹：直接删除本地目录，无需转移
   - 非空文件夹：显示确认对话框
     - "仅删除文件夹（保留文档在根目录）"：把所有子文档移到父目录
     - "删除文件夹及其内容（移入回收站）"：所有文档软删除到回收站
2. 执行相应操作
3. 更新前端树
4. 标记 workspace 为 dirty，触发 sync

**验收标准**：
- 删除前充分提示用户文件夹内容
- 非空文件夹删除需确认
- 删除后文档可从回收站恢复
- 恢复时可选择恢复到原位置或新位置

## 7. 数据模型变更

### 7.1 数据库设计决策

**Option A：隐式文件夹（推荐）**
- 不在 `documents` 表中添加 `folder_id` 外键
- 文件夹始终从 `relative_path` 推导
- 优点：无冗余，简单
- 缺点：需要在查询时计算文件夹树

**Option B：显式文件夹**
- 新增 `document_folders` 表，存储 workspace 内的文件夹元数据
- 文档添加 `parent_folder_id` 外键
- 优点：快速查询，可附加元数据
- 缺点：增加复杂性和同步难度

**决策**：**Option A（隐式文件夹）**

理由：
1. 符合 Obsidian 和现有 JType 设计（相对路径是事实来源）
2. 简化同步逻辑，文件夹操作归结为路径变更
3. 后续若需文件夹属性，可在查询时缓存或动态注入

### 8.2 Sync 中的路径变更

**当前 Sync 逻辑**：
- Pull：云端有新文档 → 本地创建
- Push：本地有新文档 → 云端创建

**文件夹操作的 Sync**：

1. **本地创建文件夹 → 自动同步到云端**
   - 创建空文件夹时不产生 sync 操作
   - 只有向文件夹添加文档时才会 push

2. **本地重命名文件夹 → 云端文档路径更新**
   - 本地所有子文档的 `relative_path` 变更
   - Sync 识别为路径变更
   - 云端更新所有文档的 `relative_path`

3. **本地删除文件夹 → 云端文档软删除**
   - 本地子文档移入 `.jtype/trash`
   - Sync 发送 `deletedPaths`
   - 云端执行软删除（移入 `document_trash`）

4. **云端删除文件夹 → 本地文件也删除**
   - 云端文档从 `documents` 表消失
   - Sync pull 发现本地有相同 `relative_path` 的文档，但云端无
   - 本地移入 `.jtype/trash`

### 8.3 文件夹结构冲突

**Conflict 示例**：本地和云端同时重命名同一文件夹

```
Local：meetings/ → meet-logs/
Cloud：meetings/ → meet-records/

Sync merge：
  检测到 relative_path 冲突
  提示用户选择：
    1. 使用本地版本（meet-logs/）
    2. 使用云端版本（meet-records/）
    3. 保留两个版本
```

## 11. 非功能性需求

### 11.1 性能

- **树展开**：展开有 100+ 子项的文件夹，UI 响应应在 200ms 内
- **拖拽**：拖拽操作应即时反馈，不阻塞 UI
- **搜索**：搜索 1000+ 文档，结果应在 100ms 内返回

### 11.2 可靠性

- **原子性**：文件夹操作（重命名、删除）应原子执行，不留中间状态
- **恢复**：App 崩溃后重启，未完成的操作应能恢复或清理
- **Sync 可靠性**：文件夹路径变更不应产生文档丢失

### 11.3 可用性

- **清晰反馈**：每个操作都显示加载、成功或错误状态
- **无歧义**：文件夹和文件的图标、颜色、排列应无歧义
- **可撤销**：重要操作（删除、重命名）应可撤销或从回收站恢复

### 11.4 跨平台一致性

- **Windows、macOS、Linux** 文件系统差异处理
  - 路径分隔符规范化（统一使用 `/`）
  - 文件名大小写敏感性处理（macOS 大小写不敏感）
  - 保留字符检查（`CON`、`PRN` 等 Windows 保留名）

## 12. 出入界定

### 12.1 在界范围内

- 文件和文件夹的 CRUD 操作
- 侧边栏树视图和展开/折叠
- 拖拽重组
- 右键菜单
- 面包屑导航
- 文件夹操作的同步
- Web dashboard 文件夹视图
- 删除到回收站

### 12.2 超出界范围

- **文件夹内容智能分类**：不实现自动文件夹建议或自动归档
- **文件夹访问权限**：不实现文件夹级别的权限控制
- **文件夹模板**：不实现创建预定义文件夹模板
- **文件夹大小限制**：不限制单个文件夹的文档数量
- **Vault 内的子 Vault**：不支持嵌套 Vault 概念
